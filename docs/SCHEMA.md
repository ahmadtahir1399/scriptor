# Scriptor — database schema

38 tables, 17 enums, RLS on everything. This document is the map. The
authoritative definitions live in `supabase/migrations/`; nothing here
overrides them.

---

## Why `user_id` is denormalised onto child tables

Almost every table in this schema carries a `user_id` column even when the
owner could be derived by following foreign keys upward. That is deliberate,
and it is the single most important design decision in the schema.

**The problem.** RLS policies run on *every row* of *every query*. If the
policy on `words` had to reach the owner through
`words → paper_uploads → papers → user_id`, Postgres would evaluate a
three-table join for each candidate row. A single thesis produces roughly
**50,000 rows in `words`**. The P7 viewer reads those rows to draw highlight
overlays, and a join-based policy would make that read slow enough to be
unusable — not "a bit sluggish", but seconds of latency on a page turn.

**The fix.** Every child table stores `user_id` directly and indexes it. Every
policy is then a single indexed equality check:

```sql
using (public.is_owner(user_id))
```

**Keeping it honest.** A denormalised column is only safe if it cannot drift or
be forged. Both are handled:

- `BEFORE INSERT` triggers in `02_functions_core.sql`
  (`set_user_id_from_paper_upload()` and friends) derive `user_id` from the
  parent row and **overwrite whatever the client supplied**. Application code
  never sets it and cannot lie about it.
- The parent FK is `ON DELETE CASCADE`, so a child can never outlive the parent
  it inherited its owner from.

**The trade.** Slightly more storage and a trigger per table, in exchange for
RLS that scales to the largest table in the system. Worth it.

## Aggregate boundaries

Seven aggregates. Each has one root; deleting the root cascades everything
beneath it. Cross-aggregate references are `SET NULL` or `RESTRICT`, never
`CASCADE`, so one aggregate can never silently delete another's data.

| Aggregate | Root | Contains |
|---|---|---|
| **Identity** | `auth.users` | `profiles`, `user_roles`, `notification_preferences` |
| **Catalogue** | *(none — reference data)* | `document_types`, `checks`, `check_versions`, `document_type_checks`, `check_ab_tests` |
| **Paper** | `papers` | `paper_uploads`, `upload_entitlements`, `paper_pages`, `words` |
| **Analysis** | `paper_analyses` | `check_results`, `findings` |
| **References** | `paper_analyses` | `in_text_references`, `bibliography_references`, `reference_pairs` |
| **Requirements** | `requirement_files` | `requirements`, `upload_requirements` |
| **Queue** | *(standalone)* | `analysis_jobs`, `token_usage` |

`todo_*` and `defense_*` hang off the Analysis aggregate but are separately
owned by the student: generated by a job, then freely edited.

## Tables

### Identity — `03_identity.sql`

| Table | Purpose |
|---|---|
| `institutions` | Universities. Optional affiliation on a profile. |
| `profiles` | Application user record, 1:1 with `auth.users`. **Holds no role column** — see below. |
| `role_definitions` | Human-readable description of each `app_role`. |
| `permission_definitions` | Human-readable description of each `app_permission`. |
| `role_permissions` | Role → permission mapping. Read by `has_permission()`. |
| `user_roles` | Role assignments. **No user write policy exists.** |

Roles live in `user_roles`, not on `profiles`, because `profiles` is
user-updatable. A role column on a row the user can update is the classic
privilege-escalation bug: update your own profile, grant yourself `ADMIN`.
Separating them makes that impossible by construction rather than by careful
policy wording.

### Catalogue — `04_catalogue.sql`

| Table | Purpose |
|---|---|
| `document_types` | Thesis categories and their `max_chars` compatibility limit. |
| `checks` | Check catalogue. Display metadata only. |
| `check_versions` | **Prompt text. Core IP.** Immutable provenance for every result. |
| `document_type_checks` | Which checks are offered for which document type. |
| `check_ab_tests` | Head-to-head prompt experiments. |
| `checks_public` *(view)* | Prompt-free projection. **This is what the app reads.** |

`check_versions` has **no SELECT grant for `authenticated`**. Ordinary users
read `checks_public`, which selects catalogue metadata and the active version
*number* but none of the three prompt columns. The view is intentionally not
`security_invoker` — running as owner is the mechanism that lets a user read
safe columns from a table they have no grant on.

### Paper — `05_papers.sql`, `06_pages.sql`

| Table | Purpose |
|---|---|
| `papers` | Stable identity for a document across drafts. |
| `paper_uploads` | One **immutable** row per submitted file. |
| `upload_entitlements` | Write-once snapshot of what an upload may do. UPDATE blocked by trigger. |
| `paper_pages` | One row per page, with structural `page_type`. |
| `words` | Per-word bounding boxes, ~50k rows per thesis. |

A revised draft **inserts a new `paper_uploads` row against the same
`paper_id`** — it never updates the old one. That is what keeps an analysis
permanently tied to the exact bytes it read, and what makes draft-over-draft
comparison possible later.

`upload_entitlements` looks pointless today because every flag defaults to
`true` and `source` is always `FREE`. It exists because entitlement is decided
**once at upload time** rather than read live off the account. An analysis from
last year keeps the entitlements it was granted even if the user later
downgrades — which turns "add paid tiers" into one prompt with no refactor.

`paper_pages.page_type` is the lever that keeps analysis affordable: a check
scoped to `BODY` never pays to read the cover page or the bibliography.

### Analysis — `07_analysis.sql`

| Table | Purpose |
|---|---|
| `paper_analyses` | One pipeline run over one upload. |
| `check_results` | One check's output. `check_version_id` is immutable provenance. |
| `findings` | Locatable issues. `quote` is NOT NULL. |

`paper_analyses` has five independent per-feature status columns defaulting to
`NONE`. **`NONE` means "not requested", which is not the same as "failed".** A
student who never asked for defense questions must not see a failure badge for
them — that distinction is the entire reason `job_status` has a `NONE` member.

`findings.quote` is NOT NULL with a non-empty CHECK because a finding the model
could not quote **cannot be anchored to a location** by P7. The seed prompts
say so explicitly and the ingestion layer drops unquotable findings rather than
storing something the viewer cannot show.

The `(word_index_start, word_index_end)` range on a finding is resolved against
`words.word_index` to compute highlight boxes.

### References — `08_references.sql`

| Table | Purpose |
|---|---|
| `in_text_references` | Every citation occurrence in the body text. |
| `bibliography_references` | Reference-list entries plus verification result. |
| `reference_pairs` | The join — **including the orphans on both sides.** |

Both FKs on `reference_pairs` are nullable, and that is the point. A null
in-text side is an uncited bibliography entry; a null bibliography side is a
citation with no entry. **The orphans falling out of this join are the
finding** — a matched pair is unremarkable.

`reference_health` defaults to `UNCHECKED`, which is distinct from `NOT_FOUND`:
we have not looked yet, versus we looked and it is not there.

### Requirements — `09_requirements.sql`

| Table | Purpose |
|---|---|
| `requirement_files` | Uploaded faculty guideline documents. |
| `requirements` | One discrete, checkable rule extracted from a file. |
| `upload_requirements` | Which rules applied to an upload, and how it scored. |

`is_mandatory` separates "must" from "should": a violated mandatory rule is
critical, a violated optional one is advisory.

### Todos & Defense — `10_todos.sql`, `11_defense.sql`

| Table | Purpose |
|---|---|
| `todo_groups` | Thematic grouping of revision tasks. |
| `todo_items` | One actionable task. `finding_id` is `SET NULL` on delete. |
| `defense_question_groups` | Thematic grouping of likely committee questions. |
| `defense_questions` | A question, its reference answer, and its source passage. |
| `defense_practices` | One practice session. |
| `defense_question_answers` | One answer in one session. |

`todo_items.finding_id` is `SET NULL` rather than `CASCADE` deliberately: if
the underlying finding disappears, the student's task and their progress on it
survive. **The task is theirs, not the analysis's.**

`defense_question_answers` is keyed by `(practice, question)` so the same
question answered in two sessions produces two rows — which is what makes
progress visible.

### Queue — `12_jobs.sql`

| Table | Purpose |
|---|---|
| `analysis_jobs` | Work queue. **Service role only.** |
| `token_usage` | Per-call LLM cost ledger. **Service role only.** |

Three properties, three mechanisms:

- **No double-claiming** — `claim_analysis_jobs()` uses `FOR UPDATE SKIP
  LOCKED`. Each worker locks the rows it selects; rows already locked are
  skipped rather than waited on. Never replace this with SELECT-then-UPDATE
  from application code — the gap between the two statements is exactly where
  two workers claim the same job.
- **No wedged jobs** — `reap_stale_jobs()` runs every 5 minutes via `pg_cron`
  and returns jobs stuck in `GENERATING` past a timeout. Without it, a crashed
  worker wedges an analysis forever and nothing ever says why.
- **Free retries** — `idempotency_key` is UNIQUE and deterministic from the
  logical identity of the work. Re-enqueuing after a partial failure creates
  only the genuinely missing jobs.

`token_usage.cached_input_tokens` is logged from day one because it is the only
way to prove prompt caching is working. Caching is the difference between a
viable and an unviable cost per analysis, and discovering six months from now
that it silently broke — with no historical baseline — is expensive blindness.

### Events — `13_events.sql`

| Table | Purpose |
|---|---|
| `upload_events` | Ingestion funnel telemetry. |
| `rate_limit_attempts` | Abuse counters. |
| `admin_actions` | Append-only audit trail. UPDATE blocked by trigger. |

None of these has a user write policy. A rate-limit row a client can delete is
not a rate limit; an audit log that can be edited is not an audit log.
`admin_actions.actor_user_id` is `SET NULL` on delete — the trail outlives the
admin who acted.

### Notifications — `14_notifications.sql`

| Table | Purpose |
|---|---|
| `notifications` | In-app feed backing the topbar bell. |
| `notification_preferences` | Per-user delivery settings, created on signup. |

Users may mark read and delete, but **not insert** — a client that can insert
here could forge system messages to itself.

## Security model — `15_rls.sql`

Default deny: RLS is enabled on all 38 tables, then policies add back exactly
what is needed. A table with RLS on and no policy is reachable only by the
service role, which is the correct posture for the queue, the cost ledger, the
rate limiter and the audit trail.

**Two enforcement layers, used together:**

- **Policies** decide which *rows* a user can touch.
- **Column grants** decide which *columns* they can write.

Policies alone are not sufficient. A row policy on `check_results` would let a
user rewrite the `feedback` they were given. The column grant is what actually
prevents that:

```sql
grant update (rating, is_helpful, user_comment) on public.check_results to authenticated;
grant update (is_resolved, resolved_at)          on public.findings      to authenticated;
```

**Shared predicates** — every policy calls one of these, never an inlined
variant:

- `is_owner(uuid)` — `STABLE`, so the planner evaluates it once per statement
  rather than once per row. On `words` that difference is the whole performance
  story.
- `has_permission(app_permission)` — `SECURITY DEFINER` with
  `SET search_path = ''`. The pinned search path is mandatory, not stylistic: a
  definer function with an unpinned path lets a caller who can create objects
  shadow the tables it reads.

**Storage** — both buckets are private. The first path segment *is* the owner
(`{user_id}/...`), and the policy compares `storage.foldername(name)[1]` to
`auth.uid()`. No public bucket exists and no public URL is generated anywhere
in the codebase; access is via short-lived signed URLs minted server-side.

**Realtime** — exactly three tables: `paper_analyses`, `check_results`,
`analysis_jobs`. Every table in the publication costs WAL decoding on every
write, and `words` alone would flood the socket with 50,000 events per upload.

## TypeScript layer

```
lib/db/types.generated.ts   generated — never hand-edit, run `npm run db:types`
lib/db/enums.ts             the ONLY place enum values exist in TypeScript
lib/domain/*.ts             composed app-facing types, one file per aggregate
lib/validations/*.ts        zod schemas for server-action inputs
lib/db/queries/*.ts         every read in the app goes through a named function
```

`lib/db/enums.ts` checks each tuple against the generated type with
`satisfies`. Add a value in SQL, run `db:types`, and any tuple that was not
updated becomes a **compile error** rather than a silent runtime gap. That
check is the whole point of the file.

`lib/db/queries/` is the DRY boundary. No component and no later prompt writes
an inline `.from(...).select(...)` — that is what keeps sixteen prompts from
each inventing a slightly different select list and diverging when a column is
added.

## Conventions

- Tables `snake_case` plural, columns `snake_case`, enums singular.
- Primary keys `id uuid default gen_random_uuid()`, except `words` and the
  event tables, which use `bigint generated always as identity` — they are
  high-volume and append-only, and a monotonic key clusters better than a UUID.
- Foreign keys `<singular_table>_id`. **Every FK declares an explicit
  `ON DELETE`**: cascade for owned children, `set null` for optional
  references, `restrict` for catalogue rows.
- Timestamps `created_at`, `updated_at`, `*_at`. Booleans `is_*` / `has_*`.
- `updated_at` is written by the shared `set_updated_at()` trigger on all 24
  tables that have it. **Never write it from application code.**
- Indexes are created in the same migration as their table.
